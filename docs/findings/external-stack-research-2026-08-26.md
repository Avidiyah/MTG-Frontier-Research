**Research date and access date:** 2026-08-26.  
**Scope:** external technical and literature review; no implementation or new corpus measurement.  
**Evidence labels:** **Repository fact** is measured or stated in this repository; **external fact** is supported by a cited primary or secondary source; **recommendation** is a decision proposal; **hypothesis** is an interpretation that still requires project evidence. ## 1. Executive summary

1. **Retain the present Rust + standard-library Python + SQLite stack through structural discovery.** The authoritative project snapshot is only 38,626 Oracle records and 78,949 rulings. SQLite's documented limits are orders of magnitude above this workload, and its actual near-term constraint is one-writer concurrency rather than dataset size [S01, S02]. There is no evidence-based migration case.
2. **Strengthen identity and lineage before adding analytical infrastructure.** A committed, content-addressed snapshot manifest and per-experiment manifest would close a more important evidence gap than DuckDB, Parquet, DVC, or MLflow. Add those systems only after a measured failure of the simpler manifests.
3. **No parser framework solves semantic interpretation.** `nom`, `pest`, LALRPOP, chumsky, and tree-sitter can recognize syntax and preserve spans; none supplies Magic referents, scope, state transitions, replacement ordering, continuous-effect layers, or rule-changing semantics [S08-S12]. Delay selection until the semantic inventory and gold data support a common spike.
4. **The mission is plausible for a majority, but the best evidence is proprietary and not a benchmark.** Wizards describes a Python Game Rules Parser that converts raw card text to CLIPS rules and says roughly 80% of newly written cards work automatically [S54]. It also documents parser extensions, engine work, hand-written CLIPS, QA failures, and thousands of regression tests [S55-S57]. This is strong existence evidence for a templated majority and equally strong evidence that the tail is a parser-engine-validation co-design problem.
5. **Separate five artifacts and gates: surface parse, semantic IR, static validation, execution, and behavioral validation.** Parse success, round-trip printing, type checking, executable output, and rules-correct behavior are distinct claims. The project should report each independently, including explicit unsupported results.
6. **Use a project-owned, Git-diffable annotation format.** A minimal schema should separately record source identity, structural units, operator candidates and arguments, references/relations, rules links and provenance, ambiguity, adjudication, and behavioral examples. INCEpTION is the best-fit annotation UI to pilot if multi-annotator work becomes a bottleneck, but its internal UIMA representation must not become the canonical dataset [S24, S25].
7. **Use formal tools narrowly.** Datalog is promising for static relational closure and provenance; SMT for bounded consistency/equivalence and counterexamples; transition-system formalisms for state-machine specification. GDL-II, PDDL, Event Calculus, and controlled languages are useful comparison lenses, not ready-made Magic IRs. Each assumes the difficult domain semantics have already been formalized [S16-S21].
8. **Existing engines solve execution infrastructure, not automatic Oracle understanding.** Forge scripts cards in a DSL; XMage uses per-card Java classes; Magarena uses scripts and a restricted grammar. They are valuable later as differential or backend references, but their large card pools do not establish unseen-text generalization [S46-S51]. GPL-3.0 projects also create integration boundaries.
9. **Audit phase.rs and Argentum before inventing an IR, but do not import them during discovery.** phase.rs exposes a typed Rust Oracle IR with source spans, warnings, unsupported nodes, and unimplemented effects; Argentum keeps hand-authored Kotlin cards as ground truth while experimenting with parser round trips and differential checks [S58-S63]. Both are active, immature, self-reported systems whose parse coverage is not executable correctness.
10. **Keep agents, simulation, and a production engine deferred.** Academic Magic agents and MCTS work begin with an already executable game model [S64, S65]. They provide no shortcut through the current structural and semantic gates.

At the current size, the relevant optimization is schema and measurement design, not database replacement. SQLite's maximum table/database limits do not remotely bind the corpus [S01]. WAL can improve reader/writer overlap, but it does not remove the single-writer boundary and is unsuitable as a network-filesystem concurrency solution [S02]. `STRICT` tables improve type enforcement without requiring a new store [S03].

Relational storage remains appropriate for cards, printings, faces, rulings, rule versions, snapshots, and links. Columnar copies become useful for repeated scans over wide derived feature matrices. A graph representation becomes useful only when relation-heavy questions such as reference chains, CR dependencies, or replacement dependencies cannot be expressed and maintained clearly as relational edge tables. Logic storage becomes useful for derived closure and invariants, not as a substitute for raw provenance. None of these future uses requires abandoning SQLite as the corpus system of record.

## 5. Semantic representation and parsing findings

### 5.1 Surface parsing

A surface parser should answer where constructs begin and end, what alternatives were considered, and which source spans support each node. It should not claim that a recognized phrase is executable. Required output properties are stable source offsets, normalized and verbatim text, recursive quotation support, ambiguity sets or diagnostics, and explicit unsupported nodes.

PEG, LR, and combinator frameworks trade grammar readability, ambiguity behavior, recovery, and semantic-action ergonomics. The adoption experiment must therefore use the same frozen, adjudicated sample and report exact/partial/unsupported/ambiguous outcomes, span fidelity, diagnostic usefulness, and maintenance effort. Throughput is secondary at this corpus size.

Hybrid parsing should mean deterministic candidate construction plus statistically assisted ranking or recovery under a formal grammar. PICARD demonstrates that constrained decoding can keep model output within a target language [S14]; it does not demonstrate correct denotation, held-out compositionality, or Magic behavior. Any learned component needs frozen splits, a novelty-aware challenge set, calibrated abstention, and a deterministic fallback. A corpus-scale learned parser before that evidence would violate the active boundary.

### 5.2 Semantic representation

A typed semantic representation must distinguish at least entities/references, operators and arguments, conditions, choices, quantities, zones, events, durations, object identity and last-known information, permissions/prohibitions, replacement/prevention, continuous modifications, and rules links. This is a requirements list, not an ontology proposal.

Attribute-grammar techniques can synthesize a node's meaning from children while inheriting bindings or context [S15]. Controlled-language systems such as ACE show how grammar, discourse representation, and anaphora resolution can be integrated [S13]. Neither makes Oracle a controlled language by declaration. The repository must first measure which constructions are controlled, which are context-supplied, and which require adjudicated alternatives.

IR nodes should carry source spans, source snapshot, parser/grammar version, rules/ruling dependencies, certainty/support status, and transformation history. A successful pretty-print or parse-print round trip proves surface preservation, not semantic equivalence.

### 5.3 Static validation

Static validation can begin before execution:

- schema/type checks: every operator has legal argument roles and zone/type constraints;
- binding checks: references have a visible antecedent or an explicit contextual source;
- totality checks: choices, durations, and unsupported branches cannot disappear silently;
- rule-link checks: referenced CR/ruling versions exist in the bound snapshot;
- dependency/stratification checks: derived relations or continuous layers have an allowed order;
- bounded constraint checks: a proposed lowering is satisfiable and preserves declared invariants.

Soufflé is a plausible engine for finite relational closure and explainable derivations [S16]. SMT-LIB/Z3 can express arithmetic and bounded equivalence/counterexample questions [S21, S23]. These validators establish consistency with manually encoded rules, not correctness of those rules.

### 5.4 Execution

Execution needs an authoritative game-state and event protocol that is absent today. The formalism comparison exposes the burden rather than selecting a winner:

| Formalism | Hidden information | Mutable state and arithmetic | Time/events | Replacement and rule-changing effects |
|---|---|---|---|---|
| Datalog | Visibility can be facts, but epistemic separation is manual | Fixed-point relations; updates and rich numeric state need staging/host code | Time steps can be indexed | Interception, ordering, layers, and self-modifying rules are non-native |
| GDL-II | `sees` and `random` explicitly model observations/chance [S17] | Finite relational successor states; arithmetic/object richness limited by encoding | Discrete turns/steps | Must be axiomatized; rule mutation is especially awkward |
| PDDL 2.1 | Not standard partial observability | Numeric fluents and action effects | Durative actions and time [S19] | Reactive replacement and continuous rules changes are not native planning constructs |
| Event Calculus | Requires epistemic/visibility extensions | Fluents change through events; arithmetic depends on implementation | Native event/interval lens [S20] | Can be axiomatized, but priority/order and layer semantics are manual |
| Transition system / TLA+ | State variables can model each player's observations | Explicit next-state actions and arithmetic | Temporal operators and traces | Expressible in a specification, but abstraction and state explosion dominate |
| SMT | Separate knowledge/state copies can be bounded | Strong typed arithmetic/arrays/sets depending on solver theories | Bounded time unrolling | Expressible as constraints only after exact precedence/meta-rules are given |

The Arena architecture is directly relevant: a base C++ rules engine executes work items while CLIPS rules modify proposed actions and effects [S54]. This suggests that replacement and permission effects may need first-class interception points, not merely sequential actions. It is evidence for an architectural requirement, not evidence that CLIPS is the correct project backend.

### 5.5 Behavioral validation

Behavioral validation requires observable initial state, choices, event trace, expected state/actions, rule-version identity, and a declared oracle. Useful layers are:

- **golden tests:** exact structural/IR serialization and diagnostics; `insta` is a maintained Rust snapshot option [S33];
- **property-based tests:** parse/serialize invariants, stable IDs, well-typed generation, and state invariants; `proptest` is suitable in Rust [S32];
- **metamorphic tests:** transformations with a separately justified semantic relation, such as alpha-renaming of bound internal IDs, not casual Oracle paraphrases [S34];
- **mutation tests:** delete/swap/alter IR nodes or expected traces and verify the suite detects the change;
- **differential tests:** compare traces against another engine or two independent encodings, while recording disagreement rather than treating either engine as authoritative [S35];
- **official-example tests:** CR examples and rulings are higher-authority behavioral constraints but rarely complete executable scenarios.

Arena's documented regression and QA failures show why parse acceptance and a few happy-path examples are inadequate [S54-S57]. The project should never calculate one undifferentiated "coverage" percentage across these layers.

## 6. Annotation and evaluation findings

### 6.1 Minimal architecture

Use a project-owned JSONL record per Oracle face/text object, versioned by an explicit schema. Do not define the final semantic ontology yet. The minimal separable layers are:

1. **Source identity:** Oracle ID, face, exact text, character-offset convention, Scryfall snapshot/hash, CR/ruling snapshot IDs.
2. **Structural units:** boundaries, parent/child quotation structure, ability class candidate, verbatim spans, segmenter output and human correction.
3. **Operator candidates and arguments:** provisional operator label, typed role labels, spans or contextual values, with ontology version.
4. **Relations:** reference/coreference, condition/consequence, choice alternatives, duration scope, parent/attachment, rules and ruling links.
5. **Context supply:** whether a value came from Oracle text, type line, keyword/CR definition, ruling, or runtime state.
6. **Review state:** annotator, timestamps, guideline version, uncertainty, alternatives, unsupported reason, adjudicator and adjudication rationale.
7. **Behavioral fixtures:** stored separately but linked by stable ID; initial state, legal choices, expected trace/invariants, and authority of the expected result.

Store character offsets plus the quoted substring and a hash so offset drift is detectable. Stable IDs should derive from immutable source identity and explicit local annotation IDs, not list position. Deterministic exporters can produce TSV views for audits. W3C Web Annotation is useful as a conceptual reference for targets, bodies, and selectors [S30], but adopting its full JSON-LD model would add complexity before interoperability is required.

### 6.2 Workflow and agreement

Create written guidelines with positive, negative, and unresolved examples. On the agreement sample, require two independent annotations before discussion, then adjudicate. Report agreement per layer: boundary F1/exact match for segmentation; labeled span/relation precision, recall, and F1; categorical agreement (for example Cohen's kappa or Krippendorff's alpha where appropriate) for labels; and raw confusion/adjudication rates. A single score can conceal systematic boundary and prevalence effects, as the IAA literature cautions [S31].

INCEpTION supports custom span/relation/chain layers, curation, and agreement workflows [S24, S25]. Pilot it only when at least two annotators are scheduled and file-based review has a measured coordination cost. Preserve the project JSONL as canonical. UIMA CAS XMI is the high-fidelity interchange; INCEpTION documents WebAnno TSV as legacy/obsolete, so it is not a safe sole archive [S25].

Label Studio is maintainable and flexible but its raw JSON is tool-specific and its generic model is less aligned with linguistic chains/curation [S26]. doccano fits classification, sequence labeling, and sequence-to-sequence tasks but is weak for a multi-relation semantic graph [S27]. brat has clean standoff spans, relations, and events but weaker modern adjudication/governance and less visible maintenance [S28]. Prodigy is offline-capable and scriptable, but its proprietary seat/license terms make it a poor default for a durable open research artifact [S29].

### 6.3 Sampling and leakage resistance

Stratify by printing era, card type/layout, mechanic and keyword family, template frequency, template/operator novelty, text/rules complexity, nested quotation/reference depth, and effect class (one-shot, trigger, continuous, replacement/prevention, permission/prohibition, rule-changing). Preserve set-by-set first-printing order as one evaluation axis, not the only distribution.

Freeze development and held-out partitions by Oracle ID before tuning. Keep all printings/text-identical variants and mechanically linked faces in one partition. Record the partition-manifest hash in every result. Do not inspect held-out errors until the declared evaluation point. A later post-cutoff set can be a genuine temporal challenge set, but Oracle revisions and reprints must be checked for leakage. Dataset documentation should state purpose, composition, collection, transformations, intended use, limitations, and maintenance, following datasheet/data-card practices [S36, S37].

**Minimum Gate 1 evidence:** double-annotated, adjudicated structural examples across strata; published guidelines; per-layer agreement; frozen manifest; error taxonomy.  
**Minimum Gate 2 evidence:** a provisional operator/argument/reference inventory; separately scored semantic annotations; explicit context dependencies and unsupported cases; behavioral fixture design; no claim of executable equivalence.

### 7.2 What these systems establish

Arena is the clearest affirmative answer to the mission's feasibility question: a production team states that a parser makes roughly 80% of newly written cards work automatically [S54]. However, this is a first-party operational estimate, not a reproducible held-out experiment. The same sources report that new card types require engine concepts and parser lexemes, unusual abilities can require hand-written CLIPS, and QA finds interaction bugs after parsing and initial tests [S54-S57]. The defensible conclusion is **"majority automation has been demonstrated in a proprietary contemporary-card workflow"**, not **"Oracle text is solved."**

phase.rs and Argentum are closer to this repository's desired inspectable pipeline than older engines. Their typed partial outputs, warnings, scaffolds, and differential checks merit source-level audit. Their claims must be decomposed into: text accepted, all spans consumed, no unsupported nodes, IR type-valid, executable, scenario-tested, and differentially conformant. A 34,000-card parse count at the first layer cannot be reported as semantic coverage.

Forge, XMage, and Magarena mostly solve downstream state/action infrastructure by accumulating scripts or classes. They may reveal reusable primitives, interaction tests, and architecture. They do not remove the need to translate unseen Oracle compositionally. Academic Magic AI work likewise begins with an engine or abstract model; determinization and MCTS studies address search under hidden information after semantics exist [S64, S65].

## 8. Provenance and reproducibility options

### 8.1 Lowest-complexity recommendation

Commit two small, validated manifest forms; continue excluding generated bulk files.

**Dataset snapshot manifest:** schema version; logical snapshot ID; each source URL and source role; Scryfall bulk object/type and upstream `id`/`updated_at` when available; retrieval UTC; effective date; byte length; SHA-256; decompression/normalization policy; CR effective date and hash; rulings snapshot identity; database schema version; producing command; repository commit; tool version; and license/terms note. Bind the SQLite database and every exported analytical copy to this manifest ID.

**Experiment manifest:** experiment ID and question; input manifest and annotation-partition hashes; exact command and arguments; repository commit and dirty-state flag; Rust/Python/tool versions; OS and architecture; random seeds if any; start/end UTC and exit status; stdout/stderr artifact hashes; output schema versions; reviewer; and interpretation document. Canonicalize manifest serialization before hashing.

This is a deliberately small subset of concepts represented by W3C PROV entities, activities, and agents [S38] and RO-Crate's packaged research-object metadata [S39]. Use those standards as vocabulary checks; do not adopt JSON-LD or a lineage service until an external interoperability requirement exists.

### 8.2 Tool comparison

| Option | What it adds | Costs and risks | Recommendation and gate |
|---|---|---|---|
| Plain committed manifests + SHA-256 | Content identity, source metadata, exact commands, artifact linkage; transparent review | Requires a small schema, validator, and discipline; does not transfer large files | **Adopt first.** Gate: every new measurement can be reproduced from a manifest or is explicitly marked unavailable/non-redistributable. |
| Existing lockfiles | Rust dependency identity and repeatable resolution | Does not capture OS/toolchain/source data; Python remains unpinned only while standard-library-only | **Retain `Cargo.lock`.** If Python dependencies are added, commit one resolver lock and record interpreter/platform. |
| DVC | Git-tracked pointer files, hashes, pipelines, optional remotes [S40] | New CLI/cache/remote governance; regenerable public bulk data may not merit storage; pointer churn can obscure the simple provenance question | **Defer.** Adopt only for multiple large, non-regenerable artifacts needed by at least two maintainers or CI. |
| DataLad / git-annex | Distributed dataset versions, annexed content, provenance workflows [S41] | Git-annex concepts and operational complexity; dependency/license implications; more system than this single local corpus needs | **Defer/reject at current scale.** Revisit for a federated multi-dataset collaboration with partial-clone/offline requirements. |
| MLflow | Experiment tracking, metrics, artifacts, model lifecycle [S42] | Service/database lifecycle and an ML-oriented object model before models or repeated runs exist | **Reject during structural discovery.** Revisit only when concurrent model experiments cannot be audited in committed manifests. |
| Nix or containers | Broader environment capture and isolation [S43] | Learning/build/maintenance cost; containers do not themselves guarantee bitwise reproducibility or data identity | **Defer.** First record toolchains and commands. Adopt a reproducible environment only after a clean-machine reproduction failure or external release requirement. |
| Software Heritage | Long-term source-code archival/reference | Not a data host and not a substitute for release metadata; the how-to page could not be retrieved during this pass [S44] | **Use at a release/gate milestone if available.** Record persistent source identifiers separately from dataset hashes. |
| Zenodo | Release archive, metadata, DOI, GitHub release integration [S45] | Immutable published versions require deliberate packaging and rights review; generated third-party data may not be redistributable | **Defer to a citable milestone.** Archive code, manifests, schemas, and redistributable small artifacts, not unreviewed Scryfall bulk files. |

Measurement drift detection should compare a small signed-off vector on every rerun: source hashes and counts; cards with/without text; rulings/rules/glossary counts; segmentation unit counts; normalized-template count; coverage/unsupported counts; schema version; and per-stratum results. A changed source hash with unchanged logical snapshot ID is an error. A changed result with identical input, code, command, and environment identities is a reproducibility failure. A changed upstream snapshot is expected drift and must never overwrite the older identity.

Structured decisions can remain Markdown records containing status, date, context, options, evidence, decision, consequences, reversibility, and measurable revisit trigger. Adding a dedicated ADR framework would not improve evidence at this stage.

## 9. Recommendations by horizon

### Adopt or investigate during the current structural-discovery phase

- **R1 — Adopt snapshot and experiment manifests.** Begin with a versioned Markdown/JSON schema and SHA-256; do not add an artifact service.
- **R2 — Extend SQLite defensively.** Plan snapshot/source identity tables, constraints, indexes, and schema-versioned migrations; introduce them only through a later implementation task with measurement-equivalence checks.
- **R3 — Specify a project-owned layered JSONL annotation contract.** Keep structural, provisional semantic, relation, context, review, and behavioral layers separable.
- **R4 — Establish stratified double annotation and per-layer agreement before calling any set gold.** Preserve the frozen held-out policy and group leakage-prone variants.
- **R5 — Audit Arena, phase.rs, mtgish, and Argentum claims against the project's evidence ladder.** Extract failure categories and representation requirements; do not import parser outputs or use them to label held-out material.
- **R6 — Add structural golden/property tests only where current measurements need them.** Behavioral tests wait for behavioral artifacts.

### Defer until semantic inventory and gold data exist

- **R7 — Defer a corpus-scale learned or hybrid semantic parser.** Constrained decoding remains a later ambiguity/ranking experiment, not the source of the ontology.
- **R8 — Defer INCEpTION deployment unless two annotators and a real curation bottleneck exist.** A small import/export pilot may occur after the canonical schema is defined.
- **R9 — Defer DuckDB, Parquet, and Polars adoption.** A read-only benchmark may be run only after repeated analyses expose a performance or interchange problem.

### Evaluate during the IR/backend decision phase

- **R10 — Run a common parser-framework spike.** Compare `nom`, `pest`, and LALRPOP on frozen adjudicated examples; keep chumsky as a watch candidate and tree-sitter out unless incremental editing becomes a requirement.
- **R11 — Spike formal validators separately from executors.** Evaluate Soufflé for relational closure/provenance, Z3 for bounded constraints/counterexamples, and an explicit transition specification for state invariants.
- **R12 — Compare IR/backend requirements, not formalism popularity.** Use GDL-II, PDDL, Event Calculus, Arena's interception model, phase.rs, and Argentum as adversarial requirement sources. Do not select any as the final IR without vertical-slice evidence.

### Defer until engine integration

- **R13 — Evaluate Forge/XMage/phase.rs/Argentum adapters only after a stable IR and authoritative vertical slice exist.** Keep differential outputs non-normative and isolate incompatible licenses.
- **R14 — Defer production simulation, telemetry, gameplay AI, MCTS, self-play, and deck construction.** They begin after deterministic rules-correct execution.

### Reject unless new evidence appears

- **R15 — Reject a database migration justified only by corpus size.** The present workload is not close to SQLite's documented limits.
- **R16 — Reject parse-count or card-pool size as semantic/executable coverage.** Require decomposed, adjudicated metrics.
- **R17 — Reject card-specific scripts as parser success.** Explicit unsupported output is preferable to concealed fallback code.
- **R18 — Reject MLflow, DataLad, an MLOps platform, or a mandatory container/Nix environment during current discovery.** Reconsider only on the operational failures in section 10.
- **R19 — Reject a final commitment to GDL-II, PDDL, CLIPS, Datalog, SMT, a proof assistant, or any parser library before the requirements matrix and common spikes.**

## 11. Risks and counterarguments

1. **SQLite may be retained too long.** Columnar tools could reduce analyst time before wall-clock limits become severe. Countermeasure: R9 permits a bounded benchmark triggered by repeated query complexity, not only failure.
2. **A manifest-first approach may create bespoke tooling.** DVC or DataLad could provide tested behavior sooner. Countermeasure: cap the manifest schema, test one clean reconstruction, and revisit if remote artifact transfer or lineage graphs become real requirements.
3. **Set-order discovery may overweight historical wording.** Modern templating could be easier and more relevant to majority automation. Countermeasure: retain chronology for novelty evidence while adding predeclared era/mechanic/frequency strata and a future temporal set.
4. **Delaying parser spikes may discard useful feedback.** A typed experimental parser can expose missing structural distinctions. Countermeasure: permit tiny disposable spikes, but do not let their AST become the ontology or touch held-out annotations.
5. **Deterministic grammar work may not scale to the long tail.** Arena's reported 20% and parser extensions support this concern [S54]. Countermeasure: design explicit ambiguity/unsupported paths and reserve constrained statistical ranking for post-gold evaluation.
6. **Arena's 80% estimate may not transfer.** It concerns newly written cards in a proprietary authoring/product workflow, likely with contemporary templating and internal metadata; the repository spans Magic history. No denominator or held-out method is public. Treat it as existence evidence only.
7. **Open parser projects may be further ahead than this review credits.** phase.rs and Argentum change rapidly, and documentation can lag code. Conversely, their large counts may substantially overstate executable behavior. Re-run the decomposed audit at tagged milestones.
8. **A project-owned annotation schema can become an accidental IR.** Operator labels may harden before semantic adequacy is known. Keep ontology/version fields, alternatives, raw spans, and context sources; require migration studies at Gate 2.
9. **Independent engine comparison can create false confidence.** Forge, XMage, or a hand-authored Argentum card can share the same misunderstanding or stale ruling. Official CR/rulings remain higher authority; disagreements are research inputs.
10. **Formal validation can validate the wrong model.** SMT satisfiability, Datalog closure, type checks, and model checking prove properties of encodings. Seed known faults, trace every axiom to authority, and keep behavioral adjudication separate.
11. **GPL boundaries may be either over- or under-cautious.** Process separation is not a universal license answer, and copying effect taxonomies may carry provenance concerns. Obtain project-specific legal review before distributing an integrated Forge/Magarena derivative.
12. **The recommended gates may slow discovery.** The alternative risk is irreproducible progress that cannot distinguish parsing from behavior. Use small stratified samples and reversible artifacts to keep gate cost proportional.

After accepting these findings, the project still needs to solve **authoritative semantics for choices, hidden information, priority, simultaneous events, durations, continuous-effect layers, replacement/prevention, and rule-changing effects**.
